## 실습 6-1 (필수) · 버퍼 크기를 바꾸면 무엇이 바뀌나

```python
MAX_LEN = 1024  # 캐시에 담을 수 있는 최대 토큰 수
```

1,024칸에서 결과는 다음과 같았습니다.

```
첫 토큰 233 ms | 이후 43.9 tok/s (48토큰)
mask [1, 1024] | K 버퍼 [1, 8, 1024, 128]
미리 잡은 KV 버퍼: 117.4 MB (1024토큰분)
```

**할 일**
`MAX_LEN`을 704(프롬프트 638 + 생성 48에 여유를 둔 값), 1024, 2048, 4096으로 바꿔 각각 실행하고 표를 만듭니다: 첫 토큰 ms, decode tok/s, KV 버퍼 MB.

**기대 결과**
- KV 버퍼는 `MAX_LEN`에 정비례합니다(2048이면 234.9 MB).
- 첫 토큰은 `MAX_LEN`이 클수록 느려집니다. prefill의 638개 위치가 버퍼 전체를 보고 mask로 가리기 때문입니다.
- decode도 `MAX_LEN`이 커지면 조금씩 느려집니다. 매 스텝 attention이 빈 칸까지 전부 읽습니다.

**힌트**
- `MAX_LEN`이 프롬프트 + 생성 길이보다 작으면 `index_copy_`가 범위를 벗어납니다. 704 미만으로 내리지 마십시오.

## 실습 6-2 (선택) · 모양이 정말 고정됐는지 확인

```python
def causal_mask(pos):
    k = torch.arange(MAX_LEN, device=device)[None, :]
    return k <= pos[:, None]
```

**할 일**
`generate`의 decode 호출 직전에 `next_id`, `pos`, `causal_mask(pos)`의 모양을 처음 세 스텝 동안 출력합니다. 같은 자리에서 이전 방식(`torch.cat` 캐시)의 k 모양도 출력해 비교합니다.

```python
# 이전 방식의 캐시 코드
if cache[L] is not None:
    k = torch.cat([cache[L][0], k], dim=2)
    v = torch.cat([cache[L][1], v], dim=2)
cache[L] = (k, v)
```

**기대 결과**
- 고정 버퍼: 매 스텝 `[1, 1]`, `[1]`, `[1, 1024]`로 같습니다.
- `torch.cat` 방식: k의 세 번째 축이 638 → 639 → 640으로 늘어납니다.

## 실습 7-1 (필수) · 재컴파일 함정 재현하고 고치기

지금의 워밍업 코드입니다.

```python
first_id = greedy(forward(ids, warm, torch.arange(ids.shape[1], device=device)))
t0 = time.perf_counter()
decode(first_id, warm, torch.tensor([ids.shape[1]], device=device))
```

본문에서는 처음에 워밍업 입력을 `ids[:, -1:]`로 잘라 넣었다가, 첫 진짜 스텝에서 17초가 걸렸습니다.

**할 일**
1. 워밍업 줄을 `decode(ids[:, -1:], warm, torch.tensor([ids.shape[1]], device=device))`로 바꿉니다.
2. 재컴파일 로그를 켜고 실행합니다.

```bash
TORCH_LOGS=recompiles uv run python work/07_compile.py
```

3. 스텝별 ms에서 첫 스텝 시간을 확인하고, 로그에 나온 재컴파일 이유를 기록합니다.
4. `ids[:, -1:].stride()`와 `first_id.stride()`를 출력해 비교합니다.
5. 원래 코드로 되돌려 재컴파일이 사라졌는지 확인합니다.

**기대 결과**
- 로그: `tensor 'ids' stride mismatch at index 0. expected 638, actual 1`.
- 잘라 낸 텐서의 stride는 `(638, 1)`, `greedy`의 결과는 `(1, 1)`입니다. 모양이 같아도 stride가 다르면 컴파일된 코드를 다시 만듭니다.

**힌트**
- 컴파일 결과는 디스크에 캐시됩니다. 첫 실행이 오래 걸려도 정상입니다(본문 첫 실행 19.6초, 이후 2~3초).

## 실습 7-2 (선택) · 컴파일 전후 연산 수와 스텝 시간

**할 일**
1. `decode = torch.compile(forward, dynamic=False)`를 `decode = forward`로 바꿔 스텝별 ms를 기록합니다.
2. 원래대로 되돌려 다시 기록합니다.
3. 두 결과의 스텝 중앙값을 비교합니다.

**기대 결과**
- 컴파일 없이 스텝 22 ms 안팎, 컴파일 후 15 ms 안팎(본문 기준 45.0 → 65.7 tok/s, 약 46%).
- 그래도 스텝이 0이 되지 않는 이유는 가중치를 읽는 시간이 남기 때문입니다. 다음 강의 주제입니다.

## 실습 7-3 (선택) · `dynamic=True`로 prefill까지

**할 일**
`prefill = torch.compile(forward, dynamic=True)`를 만들어 prefill에도 씁니다. 프롬프트를 `ids[:, :500]`, `ids`로 바꿔 가며 첫 토큰 시간과 재컴파일 로그를 봅니다.

**기대 결과**
- 길이가 바뀌어도 매번 다시 컴파일하지 않는지, 첫 토큰이 줄어드는지 확인합니다. 결과는 PyTorch 버전과 기계에 따라 다릅니다. 줄지 않으면 그 이유(prefill은 큰 행렬곱 위주라 연산을 보내는 비용 비중이 작음)를 숫자로 설명하면 됩니다.

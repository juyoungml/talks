**1.** decode 한 스텝은 층마다 다음과 같은 작은 연산으로 이뤄지고, 28층을 합치면 PyTorch 연산이 2,546번 실행됩니다. 연산 하나를 GPU에 보내는 비용은 약 6 µs로 측정됐습니다.

```python
def block(x, L, cos, sin, mask, cache, pos):
    p = f"model.layers.{L}."
    h = rms_norm(x, W[p + "input_layernorm.weight"])
    x = x + attention(h, L, cos, sin, mask, cache, pos)
    h = rms_norm(x, W[p + "post_attention_layernorm.weight"])
    x = x + mlp(h, L)
    return x
```

2,546 × 6 µs는 약 몇 ms이고, 컴파일 전 decode 스텝(약 22 ms)에서 이 비용이 무엇을 뜻합니까?

**2.** 추가한 코드는 다음 한 줄입니다.

```python
decode = torch.compile(forward, dynamic=False)
```

`torch.compile`이 하는 일로 **맞지 않는** 것을 고르십시오.

- (a) 함수를 한 번 따라가며 연산 목록을 뽑는다.
- (b) 붙어 있는 작은 연산을 하나의 커널로 합친다.
- (c) 파이썬을 거치지 않고 실행하는 코드를 만든다.
- (d) 가중치를 자동으로 INT8로 바꾼다.

**3.** `generate`에서 컴파일한 함수는 decode에만 씁니다.

```python
logits = forward(ids, cache, torch.arange(T, device=device))   # prefill
...
logits = decode(next_id, cache, pos)                            # decode
```

`dynamic=False`로 컴파일할 수 있는 것은 decode뿐이고 prefill은 그대로 두는 이유는 무엇입니까? (두 호출에 들어가는 `ids`의 모양을 비교해 보십시오.)

**4.** 본문 실행과 예시 출력의 첫 줄입니다.

```
본문: 컴파일: 19.6초 (처음 한 번)
예시: 컴파일: 2.9초 (처음 한 번)
```

같은 코드인데 컴파일 시간이 이렇게 다른 이유는 무엇입니까?

**5.** 처음에는 워밍업을 이렇게 했습니다(본문 설명대로 다시 쓴 코드입니다).

```python
decode(ids[:, -1:], warm, torch.tensor([ids.shape[1]], device=device))
```

그랬더니 첫 진짜 스텝에서 17초가 걸렸고, `TORCH_LOGS=recompiles`는 이렇게 알려 줬습니다.

```
tensor 'ids' stride mismatch at index 0. expected 638, actual 1
```

모양은 둘 다 `[1, 1]`인데 왜 다시 컴파일했습니까? 최종 코드는 아래처럼 고쳤습니다. 왜 이것으로 해결됩니까?

```python
first_id = greedy(forward(ids, warm, torch.arange(ids.shape[1], device=device)))
decode(first_id, warm, torch.tensor([ids.shape[1]], device=device))
```

**6.** 컴파일 전 decode는 45.0 tok/s, 컴파일 후 65.7 tok/s입니다. 몇 % 빨라졌습니까?

## 정답과 해설

1. 약 **15 ms**. 22 ms 중 상당 부분이 계산이 아니라 파이썬이 다음 줄을 읽고, PyTorch가 연산을 고르고, GPU에 명령을 보내는 데 쓰인다는 뜻입니다. 토큰 하나짜리 연산은 GPU에서 금방 끝나므로 이 비용이 상대적으로 커집니다.
2. **(d)** 양자화는 컴파일과 별개로 직접 해야 합니다.
3. decode의 `next_id`는 항상 `[1, 1]`이고, 캐시와 mask도 고정 크기(1,024칸)라 모양이 매 스텝 같습니다. prefill의 `ids`는 프롬프트 길이에 따라 `[1, 638]`, `[1, 500]`처럼 달라지므로 한 가지 모양에 맞춘 코드를 쓸 수 없습니다.
4. 컴파일 결과가 디스크에 캐시되기 때문입니다. 처음에는 20초 가까이 걸리고, 두 번째 실행부터는 2~3초로 줄어듭니다. 예시 출력은 캐시가 있는 상태의 실행입니다.
5. `ids[:, -1:]`로 잘라 낸 텐서는 모양이 `[1, 1]`이어도 메모리 배치(stride)가 원본 `[1, 638]`을 따라갑니다. 컴파일된 코드는 stride까지 같기를 기대하므로, 진짜 decode 입력(stride 1)이 들어오자 다시 컴파일했습니다. `greedy(...)`의 결과는 실제 decode에 들어가는 `next_id`와 같은 방식으로 만들어진 텐서라 stride도 같습니다.
6. 65.7 ÷ 45.0 ≈ 1.46, 약 **46%**. 같은 정밀도(FP16)의 Ollama는 87 tok/s입니다.

```python
def block(x, L, cos, sin, mask, cache, pos):
```

**2.** 추가한 코드는 다음 한 줄입니다.

```python
decode = torch.compile(forward, dynamic=False)
```

`torch.compile`이 하는 일로 **맞지 않는** 것을 고르십시오.

- (a) 함수를 한 번 따라가며 연산 목록을 뽑는다.
- (b) 붙어 있는 작은 연산을 하나의 커널로 합친다.
- (c) 파이썬을 거치지 않고 실행하는 코드를 만든다.
- (d) 가중치를 자동으로 INT8로 바꾼다.

**3.** `generate`에서 컴파일한 함수는 decode에만 씁니다.

```python
logits = forward(ids, cache, torch.arange(T, device=device))   # prefill
...
logits = decode(next_id, cache, pos)                            # decode
```

`dynamic=False`로 컴파일할 수 있는 것은 decode뿐이고 prefill은 그대로 두는 이유로 맞는 것을 고르십시오.

- (a) decode의 `next_id`는 항상 `[1, 1]`이고 캐시와 mask도 고정 크기(1,024칸)라 모양이 매 스텝 같지만, prefill의 `ids`는 `[1, 638]`, `[1, 500]`처럼 프롬프트 길이에 따라 모양이 달라지기 때문이다.
- (b) prefill은 한 번만 실행되므로 컴파일해도 빨라지는 부분이 전혀 없기 때문이다.
- (c) prefill은 캐시를 채우는 단계라서 `torch.compile`이 캐시에 쓰는 연산을 지원하지 않기 때문이다.
- (d) prefill의 `ids`는 decode보다 커서, 컴파일된 커널이 GPU 메모리에 들어가지 않기 때문이다.

**4.** 본문 실행과 예시 출력의 첫 줄입니다.

```text
본문: 컴파일: 19.6초 (처음 한 번)
예시: 컴파일: 2.9초 (처음 한 번)
```

같은 코드인데 컴파일 시간이 이렇게 다른 이유로 맞는 것을 고르십시오.

- (a) 컴파일 결과가 디스크에 캐시되어, 두 번째 실행부터는 처음부터 다시 만들지 않기 때문이다.
- (b) 예시 출력은 프롬프트가 더 짧아서 따라가야 할 연산 수가 적었기 때문이다.
- (c) 예시 출력은 `dynamic=True`로 컴파일해서 모양별 코드를 만들지 않았기 때문이다.
- (d) 본문 실행은 워밍업 없이 첫 스텝에서 컴파일까지 함께 쟀기 때문이다.

**5.** 처음에는 워밍업을 아래 첫 줄처럼 했습니다(본문 설명대로 다시 쓴 코드입니다). 그랬더니 첫 진짜 스텝에서 17초가 걸렸고, `TORCH_LOGS=recompiles`는 두 번째 줄처럼 알려 줬습니다. 최종 코드는 아래 마지막 두 줄처럼 고쳤습니다.

```python
# 처음 워밍업
```

모양은 둘 다 `[1, 1]`인데 왜 다시 컴파일했고, 왜 최종 코드로 해결됩니까? 빈칸을 채우십시오.

## 정답과 해설

1. 연산을 보내는 비용 **15ms** (±0.5). 2,546 × 6 µs = 15,276 µs ≈ **15 ms**. 22 ms 중 상당 부분이 계산이 아니라 파이썬이 다음 줄을 읽고, PyTorch가 연산을 고르고, GPU에 명령을 보내는 데 쓰인다는 뜻입니다. 토큰 하나짜리 연산은 GPU에서 금방 끝나므로 이 비용이 상대적으로 커집니다.
2. (d). 양자화는 컴파일과 별개로 직접 해야 합니다. 나머지 셋은 `torch.compile`이 하는 일입니다.
3. (a). `dynamic=False`는 한 가지 모양에 맞춘 코드를 만듭니다. decode 입력은 매 스텝 `[1, 1]`로 같지만, prefill의 `ids`는 프롬프트 길이에 따라 `[1, 638]`, `[1, 500]`처럼 달라지므로 한 가지 모양에 맞춘 코드를 쓸 수 없습니다.
4. (a). 컴파일 결과가 디스크에 캐시되기 때문입니다. 처음에는 20초 가까이 걸리고, 두 번째 실행부터는 2~3초로 줄어듭니다. 예시 출력은 캐시가 있는 상태의 실행입니다.
5. **`[1, 638]`** / **638** / **1** / **`next_id`**. 컴파일된 코드는 모양뿐 아니라 stride까지 같기를 기대합니다. `ids[:, -1:]`는 원본 `[1, 638]`의 배치를 따라 stride가 638이지만 진짜 decode 입력은 stride 1이라 다시 컴파일했습니다. `greedy(...)`로 만든 `first_id`는 실제 `next_id`와 같은 방식으로 만들어져 stride가 같습니다.
6. 빨라진 정도 **46%** (±1). 65.7 ÷ 45.0 ≈ 1.46, 약 **46%** 빨라졌습니다. 같은 정밀도(FP16)의 Ollama는 87 tok/s입니다.

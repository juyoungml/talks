**3.** 캐시를 쓰면서 mask도 바뀌었습니다.

# 전

def causal_mask(T, start=0):
    q = torch.arange(start, start + T, device=device)[:, None]

## 정답과 해설

1. 첫 forward (prefill) **638토큰**, 반복문 안의 forward (decode) **1토큰**. 첫 `forward`(prefill)는 프롬프트 전체 **638개**, 반복문 안(decode)은 방금 고른 `next_id` **1개**만 넣습니다. 앞 위치의 k, v는 캐시에 있으니 다시 계산하지 않습니다.
2. **k, v 헤드 수 (n_kv)** / **헤드 하나의 차원 (hd)** / **위치 축**. `view(1, T, n_kv, hd)` 뒤 transpose로 `[1, n_kv, T, hd]`가 되므로 **8**은 `n_kv`, **128**은 `hd`이고, `dim=2`는 **위치 축**입니다. 28층이 각자 따로 쌓습니다.
3. (c). `q`는 `[1, 1]`(새 토큰 1개), `k`는 `[1, 639]`(캐시 638개 + 새 1개)이고, 비교하면 `[1, 639]`가 됩니다. 새 토큰이 캐시까지 합친 639개 위치를 모두 봅니다.
4. **약 23 ms** / **거의 그대로입니다** / **새 토큰 1개** / **프롬프트 638토큰 전체**. decode 스텝은 **240 ms → 23 ms 안팎**으로, 1토큰 forward(19.5 ms)에 가까워졌습니다. 첫 토큰은 **236 ms로 그대로**입니다. prefill은 여전히 프롬프트 638토큰 전체를 읽어야 하기 때문입니다.
5. (a). 0.062는 FP16에서 계산 순서가 달라지면 생기는 반올림 수준이고, 고르는 토큰은 8번 모두 같습니다. 첫 토큰 코드를 Hugging Face 공식 구현과 비교했을 때도 점수 차이가 이 정도(최대 0.05)였습니다.
6. per_token **114688바이트**, KB로 바꾸면 **112KB**. 28 × 2 × 8 × 128 × 2 = **114,688바이트**, ÷ 1,024 = **112 KB**입니다. 앞의 2는 k와 v 두 개, 뒤의 2는 FP16 2바이트입니다.
7. (d). 첫 토큰은 236 ms 안팎으로 그대로이고, 빨라진 것은 decode입니다. 두 번째 설명은 112 KB × 40,960 ≈ 4.7 GB로 맞습니다. 그래서 Ollama는 컨텍스트 길이(`num_ctx`)를 기본값으로 작게 잡아 둡니다.

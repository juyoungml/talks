**3.** 스텝마다 읽는 양을 계산하는 코드입니다. (`MAX_LEN = 1024`, `n_layers = 28`, `n_kv = 8`, `hd = 128`)

```python

              + nbytes(W["model.embed_tokens.weight"])         # lm head

```

세 항목은 각각 약 441 MB, 311 MB, 117 MB입니다. 세 번째 항목에서 실제로 채운 칸은 650개 정도인데 1,024칸 전체를 세는 이유로 맞는 것을 고르십시오.

- (a) 모양을 고정하려고 1,024칸 전체를 attention에 넘기고, 빈 칸은 mask로 가리기 때문이다.
- (b) 생성이 끝날 때쯤에는 1,024칸이 모두 채워지므로 미리 최댓값으로 셌기 때문이다.
- (c) 버퍼를 처음에 0으로 채우는 비용을 스텝마다 나눠 넣었기 때문이다.
- (d) 빈 칸도 K, V를 계산해 채워 두어야 mask 없이 attention을 할 수 있기 때문이다.

## 정답과 해설

1. 메시지 앞의 `time.time_ns()` → **지난 요청의 프롬프트 계산을 재사용해 첫 토큰 시간이 실제 prefill보다 짧게 잡히는 것을 막음**; `"temperature": 0` → **우리 엔진의 greedy와 같은 디코딩**; `"num_predict": n` → **생성할 토큰 수를 우리 엔진과 같게**; `"think": False` → **우리 엔진의 `enable_thinking=False`처럼 생각 과정 없이 답하게**. `time.time_ns()`가 없으면 Ollama가 지난 요청의 프롬프트 계산을 재사용해서, 두 번째 요청부터 첫 토큰 시간이 실제 prefill보다 훨씬 짧게 잡힙니다. 앞부분을 매번 다르게 하면 처음부터 계산해 우리 엔진과 같은 조건이 됩니다. `temperature 0`은 greedy와 같은 디코딩으로 맞추는 설정입니다.
2. (a). 같은 FP16 모델은 `qwen3:0.6b-fp16`입니다. decode는 **91.9 대 89.8**로 앞서고(층 행렬을 INT8로 읽는 덕분), 첫 토큰은 시간이 짧을수록 좋으므로 **220 ms 대 151 ms**로 뒤집니다. 171.8은 Q4 모델의 숫자입니다.
3. (a). attention에 버퍼 1,024칸 전체를 넘기고 빈 칸은 mask로 가리기 때문입니다. 모양을 고정해 컴파일하려고 낸 비용이고, 채운 칸만 읽으면 줄일 수 있는 낭비입니다.
4. 실제로 읽는 속도 **80GB/s** (±2), 이론 대역폭 대비 **53%** (±3). 0.870 GB × 92 ≈ **80 GB/s**. 80 ÷ 150 ≈ 0.53, 이론 대역폭의 **절반 정도**(약 53%)입니다.
5. decode 속도 천장 **125tok/s** (±2), 87 tok/s는 천장의 **70%** (±4). 150 ÷ 1.2 ≈ **초당 125토큰**. 87 ÷ 125 ≈ 0.70, 천장의 **3분의 2쯤**입니다. 더 빠르게 하려면 읽을 양 자체를 줄여야 하고, 522 MB짜리 Q4 모델이 171 tok/s를 내는 이유입니다.
6. **층마다 K, V 저장** / **10배** / **고정 크기 버퍼** / **decode 컴파일**. KV cache(층마다 K, V 저장)는 3.6 → 37.9로 37.9 ÷ 3.6 ≈ **10배**입니다. 고정 크기 버퍼는 44.0 → 45.0으로 거의 그대로지만, 매 스텝 모양을 같게 만들어 decode 컴파일(+46%)을 가능하게 했습니다.
7. (c), (d). batching과 speculative decoding은 둘 다 가중치를 한 번 읽을 때 여러 토큰을 같이 계산해서 읽는 비용을 나눕니다. 4비트 커널은 읽는 양 자체를 줄이는 방향이고, prefill 경로는 빈 칸 낭비를 줄이는 방향입니다.

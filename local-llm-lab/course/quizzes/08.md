**5.** 처음에는 곱하기 직전에 FP16으로 되돌려서 곱했습니다(저장소에는 남아 있지 않아서, 본문 설명대로 다시 쓴 것입니다). decode 스텝이 24 ms에서 105 ms로 오히려 느려졌습니다. 아래 둘째 함수가 최종 코드입니다.

```python
# 처음 방식
def linear(x, key):
    w, scale = Q[key]
    return x @ (w.to(dtype) * scale[:, None]).T

# 최종 코드
def linear(x, key):
    w, scale = Q[key]
    out = torch.ops.aten._weight_int8pack_mm(x.reshape(-1, x.shape[-1]), w, scale)
    return out.view(*x.shape[:-1], -1)
```

느려진 이유와 최종 코드의 차이를 빈칸에 채우십시오.

## 정답과 해설

1. (b). **가중치를 메모리에서 읽는 일**입니다. 토큰 하나를 위해 층 28개의 큰 행렬을 전부 한 번씩 읽어야 하고, 곱셈 자체는 토큰 하나라 금방 끝납니다. 파이썬이 연산을 보내는 비용은 컴파일로 이미 줄였습니다.
2. 이 행의 scale **0.000408** (±2e-06), 0.0204의 INT8 값 **50**. scale = 0.0518 ÷ 127 ≈ **0.000408**. 0.0204 ÷ 0.000408 ≈ 50.0 → **50**. 되돌리면 50 × 0.000408 ≈ 0.0204이고, 이 행 전체의 평균 오차는 값 크기의 1% 정도입니다.
3. (b). `(int8 행렬, scale)` 한 쌍이고, `scale`은 `amax(dim=1)`이라 행마다 하나입니다.
4. (a), (b). ① 출력 점수를 직접 만드는 행렬이라 오차에 민감하고, ② 입력에서 토큰 번호의 행을 꺼내 쓰는 용도도 있습니다. 이 행렬은 lm head로 매 스텝 읽히고, embedding과 norm을 합쳐 311 MB나 되므로 나머지 두 보기는 틀립니다.
5. **FP16** / **INT8** / **커널**. 처음 방식은 INT8을 읽고, FP16을 쓰고, FP16을 또 읽으니 더 많이 읽습니다. 최종 코드는 INT8 가중치를 그대로 읽어서 **커널 안에서** scale을 곱하므로 FP16 사본이 생기지 않습니다.
6. 줄어든 층 행렬 읽기 **441MB** (±1), decode 스텝 시간 **10.2ms** (±1). 층 행렬이 882 MB → 441 MB로 **441 MB**, 절반이 줄었습니다. 1000 ÷ 97.6 ≈ **10.2 ms**로, 스텝은 11 ms 안팎(예시 출력은 9~12 ms)이 되었습니다. 답은 48토큰까지 FP16 때와 한 글자도 다르지 않았습니다.
7. (b). 읽는 정밀도가 다르므로 같은 조건이 아니고, 같은 FP16끼리는 66 대 87입니다. Q4는 169 tok/s라 Q4도 이겼다는 말은 틀리고, 48토큰 출력이 FP16과 같으므로 비교할 수 없다는 말도 틀립니다.

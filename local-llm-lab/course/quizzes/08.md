**1.** decode 한 스텝은 새 토큰 하나를 계산하면서 아래 행렬곱을 28층 전부 지납니다.

```python
q = (x @ W[p + "q_proj.weight"].T).view(1, T, n_q, hd)
k = (x @ W[p + "k_proj.weight"].T).view(1, T, n_kv, hd)
v = (x @ W[p + "v_proj.weight"].T).view(1, T, n_kv, hd)
...
gate = x @ W[p + "gate_proj.weight"].T
up = x @ W[p + "up_proj.weight"].T
return (F.silu(gate) * up) @ W[p + "down_proj.weight"].T
```

`x`는 토큰 하나(`[1, 1, 1024]`)인데 `W[...]`는 `[2048, 1024]`, `[3072, 1024]` 같은 큰 행렬입니다. 컴파일까지 마친 decode 스텝에서 시간 대부분을 쓰는 일은 무엇입니까?

**2.** 양자화 코드입니다.

```python
w = W.pop(key + ".weight").float()
scale = w.abs().amax(dim=1) / 127            # 행마다 가장 큰 값이 127이 되게
Q[key] = ((w / scale[:, None]).round().to(torch.int8), scale.to(dtype))
```

1층 `q_proj` 첫 행에서 절댓값이 가장 큰 값은 0.0518입니다. 이 행의 `scale`을 구하고, 원래 값 0.0204가 INT8로 몇이 되는지 계산하십시오.

**3.** 위 코드에서 `Q[key]`에 저장되는 것을 고르십시오.

- (a) INT8 행렬만
- (b) INT8 행렬과 행마다 scale 하나
- (c) INT8 행렬과 원소마다 scale 하나
- (d) FP16 행렬과 INT8 행렬 둘 다

**5.** 처음에는 곱하기 직전에 FP16으로 되돌려서 곱했습니다. 그 방식을 코드로 쓰면 다음과 같습니다(저장소에는 남아 있지 않아서, 본문 설명대로 다시 쓴 것입니다).

```python
def linear(x, key):
    w, scale = Q[key]
    return x @ (w.to(dtype) * scale[:, None]).T
```

decode 스텝이 24 ms에서 105 ms로 오히려 느려졌습니다. 이유를 쓰십시오. 최종 코드는 아래와 같습니다. 무엇이 다릅니까?

```python
def linear(x, key):
    w, scale = Q[key]
    out = torch.ops.aten._weight_int8pack_mm(x.reshape(-1, x.shape[-1]), w, scale)
    return out.view(*x.shape[:-1], -1)
```

**6.** 메모리를 센 코드와 출력입니다.


- (b) 우리는 층 행렬을 INT8로, `qwen3:0.6b-fp16`은 전부 FP16으로 읽으므로 같은 조건이 아니다. 같은 정밀도끼리는 66 대 87이다.

## 정답과 해설

1. **가중치를 메모리에서 읽는 일.** 토큰 하나를 위해 층 28개의 큰 행렬을 전부 한 번씩 읽어야 하고, 곱셈 자체는 토큰 하나라 금방 끝납니다.
2. scale = 0.0518 ÷ 127 ≈ **0.000408**. 0.0204 ÷ 0.000408 ≈ 50.0 → **50**. 되돌리면 50 × 0.000408 ≈ 0.0204입니다. 이 행 전체의 평균 오차는 값 크기의 1% 정도입니다.
3. **(b)** `(int8 행렬, scale)` 한 쌍이고, `scale`은 `amax(dim=1)`이라 행마다 하나입니다.
4. ① 출력 점수를 직접 만드는 행렬이라 오차에 민감합니다. ② 입력에서 토큰 번호의 행을 꺼내 쓰는 용도도 있습니다.
5. 매번 `w.to(dtype) * scale`로 **FP16 크기의 행렬을 새로 만들어** 메모리에 쓰고 다시 읽습니다. INT8을 읽고, FP16을 쓰고, FP16을 또 읽으니 줄이기 전보다 더 많이 읽게 됩니다. 최종 코드는 INT8 가중치를 그대로 읽어서 **커널 안에서** scale을 곱하므로 FP16 사본이 생기지 않습니다.
6. 층 행렬이 **882 MB → 441 MB**로 절반이 됐고, 스텝은 **11 ms 안팎**(예시 출력은 9~12 ms)이 되었습니다. 답은 48토큰까지 FP16 때와 한 글자도 다르지 않았습니다.
7. **(b)** Q4는 169 tok/s라 (c)도 틀리고, 48토큰 출력이 FP16과 같으므로 (d)도 틀립니다.

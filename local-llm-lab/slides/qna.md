# PyTorch로 Ollama 만들기 · 예상 질문과 답변

발표 중이나 끝난 뒤에 나올 법한 질문과, 그대로 말할 수 있는 답을 모았습니다.
숫자는 모두 이 레포에서 잰 값입니다. 조건은 Apple M3 Pro, Qwen3-0.6B, 회의록 638토큰 입력, 48토큰 생성, 두 번 잰 평균입니다(`site/data/scores.js`, `examples/steps/*.txt`).
"일반적으로"라고 적은 답은 이번 실험에서 재지 않은 일반 지식입니다.

## 1. 기본 개념

<a id="q1"></a>
### Q1. 토큰은 단어인가요?

꼭 단어는 아닙니다. 토크나이저가 자주 나오는 글자 묶음을 하나의 번호로 바꾼 것입니다. 이번 회의록은 채팅 템플릿으로 감싼 뒤 638토큰이 됐고, 앞부분 '회의록의 결정 사'만 해도 토큰 8개입니다. 사전에 없는 글자는 바이트 조각 2~3개로 쪼개지는데, 이 회의록에서만 100개가 넘어 전체의 6분의 1쯤 됩니다. 슬라이드 10~11쪽입니다.

<a id="q2"></a>
### Q2. attention을 한 문장으로 설명하면요?

각 위치가 질문(q)을 들고, 앞쪽 위치들의 제목(k)과 맞춰 본 뒤, 잘 맞는 위치의 내용(v)을 많이 섞어 오는 계산입니다. 뒤에 나올 토큰은 mask로 가려서 보지 못합니다. Qwen3-0.6B는 이 일을 층마다 헤드 16개가 각자 다른 질문으로 합니다. 슬라이드 27~28쪽입니다.

<a id="q3"></a>
### Q3. KV cache는 왜 k와 v만 저장하나요?

새 토큰이 앞쪽 위치에게서 필요로 하는 것이 k와 v뿐이기 때문입니다. 앞쪽 위치의 q나 MLP 결과는 다시 쓸 일이 없습니다. 그리고 mask 때문에 앞쪽 위치의 결과는 뒤에 무엇이 붙어도 바뀌지 않습니다. 실제로 토큰 하나를 붙이기 전과 후의 1층 출력을 비교하면 앞 638개 위치의 최대 차이가 0이었습니다. 슬라이드 29~30쪽입니다.

<a id="q4"></a>
### Q4. KV cache 하나로 왜 10배나 빨라지나요?

캐시가 없으면 스텝마다 프롬프트 전체를 다시 계산합니다. 48토큰을 만드는 동안 31,752개 위치를 계산했는데, 그중 처음 보는 위치는 685개뿐이라 46배를 헛돌고 있었습니다. forward 한 번은 638토큰이면 231 ms, 1토큰이면 19.5 ms라서, 새 토큰 하나만 넣으면 decode가 3.6에서 37.9 tok/s로 올라갑니다. 예상한 20 ms보다 조금 긴 건 캐시를 이어 붙이고 600개가 넘는 위치를 읽는 일이 더해졌기 때문입니다. 슬라이드 26쪽, 30쪽, 36쪽입니다.

<a id="q5"></a>
### Q5. prefill과 decode는 무엇이 다른가요?

prefill은 프롬프트 전체를 한 번에 넣어 캐시를 채우고 첫 토큰을 고르는 단계이고, decode는 방금 고른 토큰 하나만 넣는 단계입니다. 그래서 '첫 토큰까지 걸린 시간'은 prefill을, 'tok/s'는 decode를 잽니다. 이번 실험에서 prefill 시간은 입력 길이에 거의 비례했고, decode는 스텝마다 가중치를 전부 읽는 일이 시간을 정했습니다. 두 단계는 병목이 달라서 고치는 방법도 다릅니다. 슬라이드 35쪽입니다.

<a id="q6"></a>
### Q6. RoPE는 무엇이고, 틀리면 어떻게 되나요?

attention 점수만으로는 두 토큰이 몇 칸 떨어져 있는지 알 수 없어서, q와 k를 위치만큼 돌려 두는 방법입니다. 바늘이 64쌍 있고 쌍마다 도는 속도가 다르며, 가장 빠른 바늘은 한 칸에 57도쯤 돕니다. 캐시에 있는 k는 0번부터 637번까지 이미 돌려 둔 상태라 새 토큰은 638번만큼 돌려야 합니다. 실제로 새 토큰을 0번으로 돌려 보면 '1' 다음에 줄바꿈을 고르고, 그 뒤로 1, 하이픈, 줄바꿈만 되풀이했습니다. 슬라이드에서는 뺐고, 4강 영상과 사이트 4강 글(`site/ch04.html`)에서 자세히 다룹니다.

<a id="q7"></a>
### Q7. GQA는 무엇인가요?

q 헤드 둘이 k, v 한 벌을 나눠 쓰는 방식입니다. Qwen3-0.6B는 q 헤드가 16개인데 k, v 헤드는 8개만 저장합니다. 덕분에 KV cache가 토큰 하나에 112 KB이고, 16개를 다 저장했다면 두 배였을 것입니다. 슬라이드 39쪽입니다.

<a id="q8"></a>
### Q8. greedy로만 뽑던데, temperature나 sampling을 쓰면 느려지나요?

발표에서는 비교를 쉽게 하려고 1등 토큰만 고르는 greedy를 썼고, Ollama도 temperature 0으로 맞췄습니다. sampling은 이번 실험에서 재지 않았습니다. 다만 sampling은 마지막 점수 151,936개를 확률로 바꿔 하나 뽑는 일이라, 일반적으로 28개 층의 가중치를 다 읽는 forward에 비하면 작은 일입니다. 확인하려면 같은 스크립트에서 greedy 자리만 sampling으로 바꾸고 스텝별 ms를 비교하면 됩니다. 슬라이드 20쪽입니다.

## 2. 측정과 숫자

<a id="q9"></a>
### Q9. 사람이 읽는 속도는 몇 tok/s인가요? 왜 Ollama 수준을 목표로 잡았나요?

읽기 속도 메타분석(Brysbaert, 2019)에 따르면 한국어 성인은 소리 내지 않고 읽을 때 1분에 226어절쯤 읽습니다. Qwen3 토크나이저로는 토큰 하나가 1.02글자 정도라, 초당 11토큰쯤에 해당합니다. 처음 만든 엔진은 초당 3.6토큰이라 586토큰짜리 요약 한 편에 2분 43초가 걸리고, Ollama FP16(86.8 tok/s)은 같은 요약을 6.8초에 끝냅니다. 읽는 속도보다 빠르면 글이 막히지 않고 요약도 몇 초 안에 받으니, 쓰는 데 무리가 없는 Ollama 수준을 목표로 잡았습니다. 슬라이드 7쪽입니다.

<a id="q10"></a>
### Q10. 왜 한 번 잰 값이 아니라 평균인가요? 어떻게 쟀나요?

같은 코드도 실행할 때마다 10~20% 흔들리기 때문입니다. 그래서 단계마다 두 번 재서 평균을 냈고, 실행 로그 원문은 `examples/steps/`에 pass1, pass2로 남겨 두었습니다. GPU는 일을 받아만 두고 나중에 처리하므로 시계를 보기 전에 `torch.mps.synchronize()`로 끝날 때까지 기다리고, 워밍업 후에 잽니다. 두 번은 적은 편이라, 최종 과제에서는 5회 중앙값을 요구합니다. 슬라이드 16쪽, 22쪽입니다.

<a id="q11"></a>
### Q11. 처음 화면의 78.64와 점수판의 86.8은 왜 다른가요?

78.64는 터미널에서 한 번 돌린 값이고, 86.8은 같은 조건으로 두 번 잰 평균입니다. Ollama 쪽은 응답에 들어 있는 `eval_count / eval_duration`으로 쟀습니다. 또 Ollama는 이전 요청의 프롬프트 앞부분을 재사용하므로, 요청마다 맨 앞에 다른 번호를 붙여 prefill을 처음부터 계산하게 했습니다. 슬라이드 22쪽입니다.

<a id="q12"></a>
### Q12. 첫 토큰은 왜 아직 Ollama보다 느린가요?

평균으로 Ollama FP16이 155 ms, 우리 최종 엔진이 234 ms입니다. 가장 큰 원인은 6강의 고정 버퍼입니다. prefill 때 실제로는 638칸만 보면 되는데 1,024칸 버퍼 전체를 보고 mask로 가리기 때문에, 5강에서 182 ms까지 줄였던 첫 토큰이 다시 234 ms로 늘었습니다. 그리고 prefill은 컴파일하지 않았습니다. 실제 길이만 보는 prefill 경로를 따로 두는 것이 다음 과제이고, 최종 프로젝트 트랙 A입니다. 슬라이드 54쪽, 79~80쪽입니다.

<a id="q13"></a>
### Q13. M3 Pro가 아닌 다른 맥이나 PC에서는 숫자가 어떻게 되나요?

직접 잰 것은 M3 Pro뿐이라 다른 기기의 숫자는 말씀드릴 수 없습니다. 대신 decode 속도의 천장은 '메모리 대역폭 ÷ 스텝마다 읽는 양'으로 어림할 수 있습니다. 쓰시는 기기의 메모리 대역폭을 사양표에서 찾아 870 MB(우리 최종 엔진)나 1.2 GB(Ollama FP16)로 나눠 보시면 됩니다. MPS가 없는 컴퓨터는 CPU로 돌아가고, 이때 기본 dtype은 float32라 결과가 많이 달라집니다. 슬라이드 77~78쪽입니다.

<a id="q14"></a>
### Q14. Ollama는 대역폭의 70%를 쓰고 우리는 절반이라는데, 그 차이는 어디서 오나요?

계산은 이렇습니다. Ollama FP16은 스텝마다 약 1.2 GB를 초당 86.8번 읽으니 약 104 GB/s, 우리는 870 MB를 초당 92번 읽으니 80 GB/s이고, 이론 대역폭 150 GB/s와 비교한 값입니다. 왜 Ollama가 더 효율적으로 읽는지는 이번에 확인하지 않았습니다. 확인한다면 스텝을 커널 단위로 프로파일링해서 행렬곱 커널이 내는 실효 대역폭과, 커널 사이에 비는 시간을 비교해 보겠습니다. 슬라이드 78쪽입니다.

## 3. 최적화 기법별

<a id="q15"></a>
### Q15. SDPA로 바꾸면 무엇이 빨라지나요? decode는 왜 조금만 빨라졌나요?

attention 한 번의 연산이 27개에서 4개로, 실제로 메모리를 오가는 커널이 11개에서 2개로 줄었습니다. prefill에서는 중간 점수 행렬이 28층 합쳐 6 GB 남짓 오가던 것이 사라져서 첫 토큰이 73 ms 줄었습니다. decode는 점수 행렬이 40 KB뿐이라 옮길 데이터가 거의 없고, 스텝당 연산이 644번 줄어든 만큼 26 ms에서 23 ms 가까이로 빨라졌습니다. 참고로 NVIDIA GPU에서는 일반적으로 FlashAttention 계열 커널이 쓰이고, MPS의 SDPA 커널 내부는 공개 문서가 없어 다루지 않았습니다. 슬라이드 42~46쪽입니다.

<a id="q16"></a>
### Q16. 고정 KV 버퍼는 속도가 그대로인데 왜 한 건가요?

목적이 속도가 아니라 '매 스텝 같은 텐서 모양'이기 때문입니다. torch.cat은 덧붙이는 게 아니라 한 칸 큰 텐서를 새로 만들어 통째로 복사해서, 토큰 하나마다 텐서 56개가 새로 생기고 모양도 매번 바뀝니다. 1,024칸 버퍼를 미리 잡아 두고 해당 칸에 써 넣으면 모양이 고정되고, 그래야 7강의 컴파일이 한 번 만든 코드를 계속 쓸 수 있습니다. 대가는 117 MB를 미리 잡는 것과 첫 토큰이 느려진 것입니다. Ollama도 모델을 띄울 때 컨텍스트 길이만큼 KV 공간을 미리 잡습니다. 슬라이드 48~55쪽입니다.

<a id="q17"></a>
### Q17. torch.compile은 언제 다시 컴파일하나요? 실제로 겪은 문제가 있었나요?

`dynamic=False`로 컴파일했기 때문에 텐서 모양이 바뀌거나, 스텝마다 바뀌는 파이썬 정수를 넘기면 다시 컴파일합니다. 그래서 위치를 파이썬 정수 대신 GPU 텐서로 들고 다닙니다. 텐서 안의 값은 바뀌어도 괜찮습니다. 실제로 겪은 문제는, 잘라 낸 텐서가 모양은 [1, 1]로 같아도 메모리 배치(stride)가 달라서 다시 컴파일된 것이었고, 워밍업 입력을 실제 decode처럼 greedy 결과로 바꿔 해결했습니다. 첫 컴파일은 20초 가까이 걸리고, 디스크에 캐시된 뒤에는 로그 기준 3~5초 정도입니다. 슬라이드 52쪽, 61쪽입니다.

<a id="q18"></a>
### Q18. prefill은 왜 컴파일하지 않았나요?

prefill은 프롬프트 길이에 따라 입력 모양이 매번 달라서, `dynamic=False`로 컴파일하면 길이마다 새로 컴파일하게 됩니다. 이번 발표는 decode 속도에 집중했기 때문에 prefill은 그대로 두었습니다. 길이를 몇 단계로 나눠 맞추거나 동적 모양으로 컴파일하는 방법이 있지만, 이번에는 시도하지 않았습니다. 최종 프로젝트 트랙 A에서 여유가 있으면 해 보라고 남겨 둔 부분입니다. 슬라이드 61쪽입니다.

<a id="q19"></a>
### Q19. INT8로 줄이면 정확도는 괜찮나요? 답이 정말 같나요?

행마다 가장 큰 값이 127에 오도록 눈금을 정하는 방식이고, 1층 첫 행 기준으로 되돌린 값의 평균 오차가 1% 정도였습니다. 출력 점수를 바로 만드는 embedding 표(lm head)는 FP16 그대로 뒀습니다. 이 회의록에서는 48토큰까지 FP16 때와 한 글자도 다르지 않았습니다. 다만 프롬프트 하나, 48토큰 기준이라 더 긴 답이나 다른 입력에서도 같다고는 말할 수 없고, 확인하려면 처음 달라지는 위치와 그 위치의 1등·2등 점수 차이를 보면 됩니다. 슬라이드 67~68쪽, 72쪽입니다.

<a id="q20"></a>
### Q20. 왜 4비트까지는 안 갔나요?

8비트 가중치를 그대로 읽어 곱하는 커널(`_weight_int8pack_mm`)은 PyTorch에 이미 있지만, 4비트는 그대로 읽는 커널을 따로 짜야 하기 때문입니다. 정수로 줄여 놓고 곱하기 직전에 FP16으로 되돌리면 큰 행렬을 매번 새로 만들어 읽는 셈이라, 실제로 해 보니 컴파일 없이 잰 decode가 4배 넘게 느려졌습니다. Ollama 안의 llama.cpp는 이런 커널을 Metal 셰이더로 직접 짜 뒀고, 그래서 Q4 모델이 169.1 tok/s가 나옵니다. 4비트 실험과 아직 FP16인 lm head 311 MB를 줄이는 일은 최종 프로젝트 트랙 C로 남겨 두었습니다. 슬라이드 66쪽, 69쪽, 80쪽입니다.

## 4. Ollama, llama.cpp, vLLM 비교

<a id="q21"></a>
### Q21. 결국 Ollama보다 빠르게 만든 건가요?

decode 숫자만 보면 92.2 대 86.8이지만, 공정한 비교는 아닙니다. 우리는 층 행렬을 8비트로 읽고 Ollama FP16 모델은 전부 16비트로 읽습니다. 같은 정밀도끼리는 7강의 65.7 대 86.8이 맞는 비교이고, 정밀도를 더 낮춘 Ollama 4비트 모델은 169.1 tok/s입니다. 첫 토큰도 아직 Ollama가 빠릅니다. 슬라이드 72쪽, 76쪽입니다.

<a id="q22"></a>
### Q22. Ollama, llama.cpp는 우리 엔진과 무엇이 다른가요?

Ollama는 llama.cpp를 엔진으로 쓰고, 그 위에 모델 내려받기와 관리, 로컬 서버 API를 얹은 도구입니다. llama.cpp는 C/C++로 짠 추론 엔진이고, 4비트 같은 양자화 가중치를 그대로 읽는 커널을 기기별로 직접 갖고 있습니다. 우리 엔진은 한 모델, 한 요청, greedy만 하는 170줄짜리 교육용 코드입니다. 대신 원리는 같아서, decode가 가중치를 읽는 속도에 묶인다는 계산은 Ollama의 숫자에도 그대로 맞았습니다. 슬라이드 78쪽입니다.

<a id="q23"></a>
### Q23. vLLM의 PagedAttention, continuous batching, speculative decoding은 왜 안 다뤘나요?

이번 발표의 범위가 노트북에서 한 사람이 요청 하나를 보낼 때의 기본 원리였기 때문입니다. 셋 다 잘 알려진 기법이라 간단히 말씀드리면, PagedAttention은 KV cache를 작은 블록 단위로 나눠 관리해서 여러 요청이 메모리를 낭비 없이 나눠 쓰게 하는 방법이고, continuous batching은 끝난 요청 자리에 새 요청을 스텝 단위로 끼워 넣어 배치를 계속 채우는 방법입니다. speculative decoding은 작은 모델이 초안을 여러 토큰 쓰고 큰 모델이 한 번에 검사하는 방법입니다. 배치와 speculative decoding은 결국 '가중치를 한 번 읽을 때 일을 얼마나 많이 시키나'라는 같은 질문으로 돌아가고, 마지막 슬라이드에서 다음 방향으로 짚었습니다. 슬라이드 80~81쪽입니다.

<a id="q24"></a>
### Q24. GPU 서버라면 병목이 어떻게 달라지나요?

이번 실험에서 재지는 않았지만, 일반적으로 요청 하나의 decode는 서버 GPU에서도 메모리 대역폭에 묶입니다. 서버 GPU는 대역폭이 훨씬 커서 천장 자체가 높아집니다. 그런데 서버는 보통 여러 요청을 한 번에 처리하므로, 가중치를 한 번 읽어 여러 토큰을 계산하게 되고 배치가 커질수록 병목이 계산 쪽으로 옮겨 갑니다. 그때는 동시 요청 수를 KV cache가 차지하는 메모리 용량이 제한하게 되는데, PagedAttention 같은 기법이 이 문제를 다룹니다. 연산을 하나씩 보내는 비용은 CUDA에서도 생기고, 일반적으로 CUDA Graphs나 torch.compile로 줄입니다.

## 5. 실무와 확장

<a id="q25"></a>
### Q25. 더 큰 모델에도 이 코드가 그대로 되나요?

층 수, 헤드 수, 차원을 `config.json`에서 읽기 때문에 Qwen3 계열이면 대부분 그대로 동작할 것으로 봅니다. 다만 출력에 embedding 표를 다시 쓰지 않는 모델(`tie_word_embeddings`가 `false`)은 `lm_head.weight`를 따로 써야 합니다. 1.7B 같은 큰 모델은 직접 재 보지 않았고, 이것이 최종 프로젝트 트랙 B입니다. 속도는 같은 계산으로 어림할 수 있습니다. 스텝마다 읽는 양(층 행렬, lm head, KV 버퍼)이 커지는 만큼 천장이 내려갑니다.

<a id="q26"></a>
### Q26. KV cache 메모리는 어떻게 계산하나요?

층 수 × 2(k와 v) × KV 헤드 수 × 헤드 차원 × 숫자 하나의 바이트 수를 곱하면 토큰 하나 몫이 나옵니다. Qwen3-0.6B는 28 × 2 × 8 × 128 × 2바이트라 토큰 하나에 112 KB입니다. 이번 회의록 646토큰이면 74 MB, 1,024칸 고정 버퍼는 117 MB이고, 최대 길이 4만 토큰 넘게 채우면 4.7 GB로 모델 가중치 1.2 GB보다 훨씬 큽니다. Ollama가 컨텍스트 길이를 기본으로 작게 잡는 이유 중 하나입니다. 슬라이드 38~39쪽입니다.

<a id="q27"></a>
### Q27. 여러 요청을 배치로 처리하면 더 빨라지나요?

이번 엔진은 배치를 구현하지 않았습니다. 원리상으로는 decode 한 스텝이 가중치를 한 번 읽을 때 여러 요청의 토큰을 함께 계산하면 읽는 비용을 나눠 낼 수 있어서, 전체 처리량이 올라갑니다. 대신 요청마다 KV cache가 따로 필요해서 메모리가 늘고, 요청마다 길이가 달라 위치와 mask를 따로 다뤄야 합니다. 요청 하나의 체감 속도가 빨라지는 것과는 다른 이야기라는 점도 구분해야 합니다. 슬라이드 80쪽입니다.

<a id="q28"></a>
### Q28. NVIDIA GPU, CUDA에서도 이 코드가 돌아가나요?

이 레포의 코드는 MPS가 있으면 MPS, 없으면 CPU를 쓰도록 되어 있고, CUDA에서는 돌려 보지 않았습니다. 장치를 `cuda`로 바꾸고 `torch.mps.synchronize()`를 `torch.cuda.synchronize()`로 바꾸면 대부분 그대로 갈 것으로 봅니다. 다만 INT8 커널(`_weight_int8pack_mm`)이 쓰시는 PyTorch 버전과 GPU에서 지원되는지, 속도가 어떤지는 직접 확인해야 합니다. 숫자는 기기마다 다르니, 각 단계의 tok/s를 직접 재서 비교하시는 것을 권합니다.

<a id="q29"></a>
### Q29. 실무에서 추론 엔진을 직접 짤 일이 있나요?

대부분은 Ollama, llama.cpp, vLLM 같은 도구를 쓰시면 됩니다. 이 발표의 목적은 엔진을 대체하는 것이 아니라, 그 도구가 내는 숫자를 읽는 눈을 갖는 것입니다. 예를 들어 '스텝마다 읽는 양 × tok/s'를 대역폭과 비교하면, 어떤 기기와 어떤 양자화를 고를지, 컨텍스트 길이를 얼마로 잡을지 미리 어림할 수 있습니다. 슬라이드 81쪽입니다.

## 6. 발표자와 코스

<a id="q30"></a>
### Q30. 코드는 어디 있고, 직접 따라 하려면 어떻게 하나요?

강의 사이트는 juyoung.site/talks, 코드는 github.com/juyoungml/talks의 `local-llm-lab` 폴더에 있습니다. `steps/01_first_token.py`부터 `steps/09_compare.py`까지 강마다 실행되는 파일이 하나씩 있고, 실행 로그 원문도 `examples/steps/`에 있습니다. `uv sync --python 3.12`로 환경을 맞춘 뒤 `uv run python steps/04_kv_cache.py`처럼 실행하면 되고, 처음 실행할 때 모델 가중치 약 1.2 GB를 받습니다. Ollama와 비교하려면 `ollama serve`를 띄우고 `qwen3:0.6b-fp16`을 받아 두면 됩니다. 슬라이드 1쪽, 82쪽의 QR 코드로도 들어갈 수 있습니다.
